# Publication goals and execution plan

Updated: 2026-10-13. Owner: Shashank and research team.

## Goal and scope

Target a strong database research publication, preferably SIGMOD/PVLDB or a
comparable journal. A functioning capstone demo is an intermediate milestone.
Acceptance cannot be promised; claims must follow reproducible physical evidence.

Research question: when should Iceberg compaction run relative to forecast query
and ingestion demand, balancing maintenance interference against the cumulative
cost of postponement, with explicit handling of prediction uncertainty?

Compaction remains Iceberg's existing operation. Our contribution is predictive
maintenance timing. The scheduler must anticipate a quiet window or an approaching
burst, rather than merely react to the current CPU value.

## Non-negotiable working rules

  results, synthetic training augmentation, or synthetic substitutes for missing
  workload traces. Do not silently downgrade a run when infrastructure is absent.
- Use proper, verified datasets and physical Spark/Iceberg execution for all runs.
  Benchmark data generated by the official TPC-H generator is legitimate benchmark
  data; fabricated experimental outcomes are not. Record generator provenance.
- Missing datasets, failed connections, inadequate data, incompatible models, or
  failed table resets must stop an experiment with an explicit error.
- No unexplained hardcoded predictions, fragmentation increments, calibration
  offsets, starvation counters, or production policy thresholds. Necessary values
  such as ports, horizons, sampling intervals, engine settings, and risk budgets
  must be named configuration with a source or justification. Baseline thresholds
  must be faithful to cited methods or tuned on training data, never test data.
- No dummy-data test runs. Prefer static checks and validation of recorded physical
  artifacts. New live validation must use a dedicated verified benchmark table.
  Existing mock/synthetic tests are historical interface tests, not evidence.
- Be a harsh, evidence-based reviewer. State uncertainty and negative results;
  distinguish implemented features, measured behavior, and proposed mechanisms.
- Preserve historical artifacts. Mark unsupported claims; do not overwrite raw
  evidence or silently remove failed experiments.
- After each prompt that changes the repository: verify, commit only intended
  changes, push to GitHub, sync local and worker3, and compare HEAD and intended
  file hashes. Preserve unrelated dirty/untracked files; never force a reset.
- Protect active runs from code/configuration changes. Future runs must use a
  recorded immutable checkout/configuration, not a changing working directory.

## Intended architecture

1. Model A estimates query latency/interference during physical compaction,
   conditioned on workload, query characteristics, table state, and rewrite size.
2. Model B estimates query performance without maintenance as fragmentation grows.
3. Model C forecasts future query arrivals, query mix, and ingestion using only
   information available at the decision time. CPU alone is action-dependent.
4. Measured transition estimates predict rewrite duration, post-rewrite layout,
   and fragmentation growth. Begin with empirical estimates, not extra complexity.
5. The scheduler evaluates candidate start times over a common horizon, including
   waiting, rewriting, and post-rewrite periods; executes the first action and
   replans with new observations.
6. Uncertainty applies to the difference between competing plans. Comparing two
   upper bounds does not itself guarantee safe decisions. Fallback and maintenance
   constraints must be justified, configurable, and evaluated.

Recent CPU averages describe history; they are not future forecasts. The current
two-model policy and fixed `+2` file projection do not implement this architecture.
Forecasting does not imply access to the workload generator's future trace.

Model count is not fixed as a research requirement. See
`docs/architecture_choice_and_validation.md` for the proposed comparison between
separate A/B models and a shared action-conditioned cost estimator plus demand
forecaster. No architecture winner has been validated or implemented yet.

## Research questions and success criteria

- RQ1: Can maintenance interference and fragmentation penalties be predicted on
  held-out physical experiments better than simple per-query baseline estimates?
- RQ2: Does future-demand forecasting improve timing beyond current-load policies
  and the two-model policy, at comparable maintenance progress?
- RQ3: Does uncertainty handling improve behavior when forecasts are inaccurate or
  workloads shift? Measure coverage, width, decision regret, and fallback frequency.
- RQ4: What latency/resource/maintenance-debt tradeoff is achieved, and where does
  the method fail across query mixes, data sizes, and interference conditions?

Require repeated, held-out physical runs and explicit limitations. No result is
accepted merely because it matches the desired hypothesis or a target MAE.
Conformal prediction is not an unconditional safety guarantee under time dependence
or distribution shift. Learned delay cost does not prove starvation impossible.

## Evaluation design

Compare periodic maintenance, tuned storage thresholds, current-load/off-peak
heuristics, the two-model scheduler, no-uncertainty ablation, the full method, and
an explicitly labelled future-aware oracle. The current AutoComp-named heuristic
must not be called a faithful reproduction until checked against the paper.

Use verified trace-driven arrivals and ingestion, with holdout by trace/time block
and appropriate gaps for overlapping windows. No test-based tuning. Match offered
workload, initial snapshots, resource budgets, and useful maintenance completion.
Report per-query tail latency, throughput, SLA violation rates, rewrite bytes/files,
maintenance debt, overhead, uncertainty coverage/width, and run-level intervals.
Repeated windows within one run are not independent experimental repetitions.
Select repetition count and statistical methods from pilot variance and design,
not a universal magic count. Document workload provenance and baseline parameters.
