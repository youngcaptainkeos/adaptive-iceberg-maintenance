# Repeated development timing-headroom experiment

Explicitly authorized21October after the successful submission-overhead diagnostic. This is a new controlled physical timing study, not completion of the old7/0/1 cohort and not a fresh independent-family performance test.

## Frozen design before physical outcomes

- Same verified Snowset-mapped20-minute development source window as corrected old arm01:3,094 original arrivals, unchanged source IDs/timestamps/round-robin query mapping. All queries drain naturally; no thinning/scaling/synthetic fallback. One staticTPC-HSF1lineitem table (6,001,215rows),16initial files and at mostone real Iceberg rewrite per arm; fresh eight table identities.
- Four interventions: first controller opportunity after0,60or600seconds, plus no maintenance.0is immediate;60is one established decision interval and the earlier controller's candidate wait;600is the midpoint of the registered1200s arrival horizon. These are preregistered experimental settings, not policy predictions. Actual SQL submission lag is retained; a missed intervention cannot pass as a null control.
- Two complete repeats in forward/reverse order: [start0,start60,start600,noaction], then [noaction,start600,start60,start0]. This balances each intervention's early/late placement across the eight-run sequence. It is not independent-day replication, randomization or a power calculation. No third repeat selected from outcomes and no stopping early because effects are unfavorable.
- Primary outcome: sum of original scheduled-arrival→actual-result response times over all original arrivals through drain. Report waiting, actual calls, drain, requested/actual maintenance timing, rewrite count/duration and final file state separately. No invented scalar SLA, cloud cost or future-work penalty.
- Fixed historical empirical model and past-demand source remain byte-bound for runner compatibility, but fixed interventions do not use a forecast or model to choose their times. No fitting or new counterfactual labels.

## Integrity and final comparison

Original strict source multiset, SQL/snapshot/results, actual Spark tasks,60/300s telemetry coverage/freshness, FIFO/request identity and exact integer response-area gates remain. Added fixed-time audit requires one actual rewrite, no early submission and exact decision-rule behavior. Resource locks and actual Spark-idle checks precede each child. Never reuse occupied tables, kill/restart services/processes or delete data.

Before physical work, a detached real-source preflight exercises all four interventions on previously recorded elapsed frontiers and actual queue rows, parses/imports source, verifies hashes and checks real GitHub documentation-push capability. No synthetic scenario is used. Final comparison requires all eight arms, binds saved results/protocols, reconstructs every raw episode and replays decisions, checks matching source/layout/model and reports **all** contrasts. Partial collections retain failures/unattempted scope with no survivor comparisons.

Consistent-headroom flag means the same delayed intervention has lower actual total response than immediate in both repeats. This is descriptive, not a confidence interval, causal-generalization claim or minimum-effect success threshold. Negative/inconsistent outcomes are retained. No policy improvement, calibration or novelty follows automatically.
